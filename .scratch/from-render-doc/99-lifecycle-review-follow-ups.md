## Restart and stop

- [x] **`/_/restarting` has no generation.** *(PR 489, merged as bdfeadc0: `POST` returns a token, `DELETE ?token=N` forgets only that announcement; with no token it clears whatever is announced, so the race stays open for a client that never read a token. Red check on t-compute against the source of bdfeadc0^1 with the new tests on top: `test_a_restart_announced_returns_a_token_the_take_back_must_carry` and `test_a_take_back_with_the_current_token_forgets_the_announcement` fail with `KeyError: 'token'`, `test_a_take_back_whose_token_is_not_a_number_is_refused` with `200 == 400`; 3 failed.)* Two overlapping `sheaf restart` runs let A's `DELETE /_/restarting` clear B's newer announcement (`src/sheafmd/lifecycle.py:117`, `:149`; `src/sheafmd/hub/core.py:1327-1337`). Fix idea: a token returned by `POST` and required by `DELETE`.
- [x] **A lost answer to `POST /_/restarting` leaves the announcement up.** *(PR 489: the command now takes the announcement back before reporting the lost hub, the service is not asked. Red check as above: `test_a_restart_announcement_whose_answer_was_lost_is_taken_back` fails with the `DELETE` missing from the requests the hub saw.)* If the POST succeeds on the hub but its answer is lost (`HubLost`), `via_service` never sets `told` (`src/sheafmd/lifecycle.py:149-150`), so a later manager failure does not take the announcement back.
- [x] **A cancelled Tell delivery that cannot be killed is not counted as busy.** With no stop job started, it is not counted by `Hub.busy()` (`src/sheafmd/hub/core.py:1339-1346`), so a non-forced upgrade stop can proceed over it. Unproven: reproduce first. *(PR 508, merged as 7ec08475: reproduced red on t-compute first (`busy()` was False, `test_a_cancelled_delivery_that_has_not_ended_still_holds_an_upgrade_stop_back`); `Hub.busy()` now counts a cancelled delivery until its worker ends. Residual: a worker that never ends holds a non-forced upgrade stop back; `sheaf restart` forces.)*
- [x] **A newer command meeting a plain stop already under way.** `request_stop("upgrade")` returns True and leaves reason `stop` (`src/sheafmd/hub/core.py:1307-1314`); the hub exits 0, the service does not restart it, and `_meet_version` reports "the hub did not come back on the new version" (`src/sheafmd/hub/client.py:418`). Decide what the command should say or do. *(PR 508: `POST /_/stop` answers `{ok, reason}`; a hub that answers it makes the newer command fail with `the hub is being stopped; ...` (exit 1) and start no hub, SPEC 8.4 says so. Limit: the hub a newer command meets is always older and answers no reason, so against today's hubs the old `did not come back` error stays (same exit 1) until a hub of this version meets a newer command.)*
- [x] **`on_stop` is called outside `_stop_lock`.** `Hub.request_stop` calls `on_stop` after leaving the lock (`src/sheafmd/hub/core.py:1323-1324`), so two callbacks can arrive in the opposite order of their decisions. Harmless today; document it or call it under the lock. *(PR 508: documented in the code comment and SPEC 8.4; not moved under the lock because the callback takes locks of its own)*
- [x] **A nested signal during a stop has not been reviewed.** The SIGTERM handler runs `request_stop` (holding `admit` and `_stop_lock`, both re-entrant) on the main thread; what a nested signal can reach through `on_stop`/`announce_stop` is unreviewed. *(PR 508 review, no code change: the handler runs on the signal thread (main in the no-siginfo fallback), `request_stop` takes only `admit` and `_stop_lock` (both re-entrant), `_on_stop` sets an event and starts a thread, and the signal reason never calls `busy()`)*
