# Ticket 06 : plan du bouton micro dans la boîte de chat

Ce plan dit comment la boîte de chat des commentaires sheaf reçoit un bouton micro : comment la page enregistre et envoie le son, quel service transcrit dans chaque cas, comment le hub sait qu'il peut proposer le bouton, quelle politique de sécurité le micro demande, ce qui est testé, et ce que SPEC change. Aucun code n'est écrit ; le plan est à relire avant.

Légende : **[vu]** = lu ou mesuré pendant cette session (source et date donnés). **[non vu]** = déduit ou venu de mémoire, à vérifier avant ou pendant l'implémentation. Rien de [non vu] n'est une décision.

## Les deux situations de la page

La page tourne de deux façons [vu, page.js:12-27] : dans un document à elle (page du hub, `MOUNTED` faux) ou montée dans la page de l'hôte par `mount.js` (`MOUNTED` vrai, dans un shadow root, sans iframe : `iframe` est dans la liste de ce que `mount.js` jette [vu, mount.js:50]).

| Situation | Qui sert la page | Qui transcrit | Le navigateur appelle |
|---|---|---|---|
| Hub du laptop (`MOUNTED` faux, sans `[proxy]`) | le hub, sur `127.0.0.1` | t-compute, par le hub | `POST /_/transcribe` sur le hub (`connect-src 'self'` suffit) |
| Montée dans tiroir (`MOUNTED` vrai, mode proxy) | Open WebUI charge `mount.js` | Open WebUI | `POST /api/v1/audio/transcriptions` sur l'origine d'Open WebUI |
| Hub en mode proxy mais page non montée (`CFG.proxy` vrai, `MOUNTED` faux) | le hub, via Caddy | **non décidé** : voir « décision A » | |

Le choix se fait dans la page par `MOUNTED`, pas par détection d'hôte : une page montée est toujours dans l'origine d'Open WebUI [vu, SPEC 9.9].

## Comment la page enregistre et envoie le son

1. **Bouton** `.rd-mic` dans `.rd-actions`, à côté de la flèche, créé seulement quand la disponibilité (plus bas) est vraie, et seulement si `navigator.mediaDevices?.getUserMedia` et `window.MediaRecorder` existent. `127.0.0.1` est un contexte sûr, le micro y est permis ([non vu] ici, comportement standard de Chrome ; à vérifier au test à la main). Une page du hub ouverte par une adresse `http://` non locale n'a pas `mediaDevices` : pas de bouton, sans message.
2. **Clic 1** : `getUserMedia({audio: true})`, puis `MediaRecorder`. Le bouton devient « arrêter » (rond rouge, `aria-pressed`, info-bulle « Stop »). Le champ reste éditable. Durée maximale 120 s, après quoi l'enregistrement s'arrête seul.
3. **Format** : le type que le navigateur accorde, choisi par `MediaRecorder.isTypeSupported` dans l'ordre `audio/webm;codecs=opus`, `audio/webm`, `audio/mp4`, `audio/ogg;codecs=opus`. Le nom de fichier envoyé reçoit l'extension du type (`dictee.webm`, `dictee.mp4`, `dictee.ogg`), parce que les deux services jugent sur l'extension [vu : t-compute `routes/audio.py:30`, hôte, 2026-11-12 ; Open WebUI : liste d'extensions de stt-read.md]. Safari produit du `audio/mp4`, Chrome et Firefox du `webm` ou `ogg` ([non vu] ici ; connaissance générale à vérifier au test sur l'iPhone du ticket 03).
4. **Clic 2** (ou la limite) : on arrête, on assemble les morceaux en un `Blob`, on libère le micro (`track.stop()` sur chaque piste, pour que le voyant du navigateur s'éteigne), et on envoie. Pendant l'envoi le bouton est désactivé et dit « Transcribing… » ; le champ reste éditable.
5. **Résultat** : le texte est inséré **à la position du curseur** du champ (ou ajouté s'il n'y a pas de sélection), avec une espace de séparation si le caractère avant n'est pas une espace ou un retour à la ligne, puis un événement `input` est déclenché pour que le brouillon (10.8) et le reste de la boîte suivent comme pour une frappe. Le curseur est placé après le texte inséré. Rien n'est envoyé à l'agent : la personne relit, corrige, envoie avec Entrée ou la flèche.
6. **Échec** (refus du micro, réponse non 2xx, délai dépassé, texte vide) : une ligne `role="status"` sous le champ, dans la langue de la page, par exemple « Microphone blocked: allow it for this site. » ou « The transcription did not work. Try again. », qui disparaît au prochain clic. Le texte déjà tapé n'est jamais touché. Un 503, un 401, un 404 ou une erreur réseau remet aussi la disponibilité à faux pour 60 s (le bouton disparaît si l'échec montre que le service est parti : un 401 est une session expirée, un 404 un hôte sans la route). Amendé à la PR 2 (Halima, 2026-11-12) : le plan disait 503 et réseau seulement.
7. **Fermeture de la boîte, Échap, changement de fil, démontage** pendant un enregistrement : on arrête l'enregistrement et on **jette** le son (rien n'est envoyé) ; pendant un envoi en cours, la réponse tardive est ignorée si le champ d'origine n'est plus dans la page. La page n'a pas de registre général de nettoyage : `listen()` ne retire que des écouteurs [vu, page.js:30-33] et `unmount()` est à page.js:3946. Le plan ajoute donc une fonction `stopDictation(discard)` explicite, appelée par `unmount()`, par la fermeture du formulaire (`textForm`), par Échap, par le changement de fil et par la perte de disponibilité ; elle arrête l'enregistreur, appelle `track.stop()` sur chaque piste et, si `discard`, jette les morceaux. Un test (point 5) vérifie chacun de ces appels.
8. **Un seul enregistrement à la fois** dans la page. Le son n'est jamais gardé : ni dans `localStorage`, ni dans le store des brouillons, ni dans le fichier du document.

Taille : 120 s de `webm/opus` pèse de l'ordre de 100 à 200 ko ([non vu], estimation) ; la limite de corps du hub est 8 Mio [vu, handler.py:47]. Le hub refuse au-delà de **2 Mio** sur cette route (413), très au-dessus de 120 s.

**Décision de plan : le navigateur n'appelle jamais t-compute. Le hub sert de relais.** Raisons :

1. La clé est une clé de flotte ; la mettre dans une page la remettrait à tout script de la page et à quiconque ouvre les outils du navigateur.
2. La CSP de la page est `connect-src 'self'` [vu, `auth.py:72`] : un appel direct est refusé par le navigateur, et l'ouvrir élargirait la politique de toutes les pages pour un seul bouton.
3. Le hub connaît déjà l'identité (cookie, 9.3) : on ne relaie que pour une personne connectée.

**Route** : `POST /_/transcribe` sur le hub, authentification cookie (comme `/_/export` [vu, page.js:1217]), contrôles Host et Origin existants (9.2). **Déclaration** : `COOKIE` a `raw_body` faux, et le corps y serait lu comme du JSON [vu, handler.py:158 et la lecture du corps plus bas] ; le plan ajoute une déclaration `COOKIE_RAW = Who(frozenset({"cookie"}), _BROWSER, raw_body=True)`, sur le modèle de `DOOR` [vu, handler.py:161]. **Exclusion de la socket proxy** : `_for_members` n'admet que les routes dont le `Who` est dans `(COOKIE, EITHER, MEMBER, MINT)` [vu, handler.py:445] ; `COOKIE_RAW` n'y est pas (c'est une valeur différente de `Who`, `Who` est un dataclass figé, comparé par valeur, `raw_body` compris [vu, handler.py:138-146]), donc la route répond 404 sur la socket proxy sans autre code. Un test le garde (point 4). Corps : le fichier audio brut, `Content-Type: audio/…`, plus `X-Filename`, qui doit correspondre exactement à `^dictee\.(webm|mp4|ogg)$` (sinon 415) ; le nom envoyé à t-compute est ce nom fixe, jamais une valeur libre, donc rien à échapper dans le multipart ; **pas** de multipart côté page, pour ne pas écrire d'analyseur multipart dans le hub : le hub construit lui-même le multipart vers t-compute avec le module standard. Réponse du hub : `{"text": "…"}` ou une erreur courte et sûre (jamais le texte d'erreur brut de t-compute, qui peut contenir des chemins). Le hub envoie `X-Priority: high`, un délai de 30 s, et ne suit pas de redirection. Un seul relais à la fois par hub (verrou, comme l'export PDF [vu, SPEC 6.5]) ; un second reçoit 429. **Budget** : au plus 12 relais par minute et 120 par heure pour le hub (fenêtre glissante, 429 au-delà) ; la route refuse (503) tant que la disponibilité est fausse, sans appeler t-compute ; chaque relais écrit une ligne de diagnostics (voir 15) avec le nom de la personne, les octets et le résultat. Les chiffres sont des valeurs de départ [non mesurées], réglables dans `[transcribe]`.

**Configuration du hub** : une table `[transcribe]` dans `config.toml` (4.3), par exemple `url = "http://100.117.2.45:8080/api/v1"` et `key_file = "~/.config/tiroir/serge-compute.env"` avec `key_name = "RAG_API_KEY"` : le **chemin** du fichier, jamais la clé ; la clé est lue au moment de l'appel, jamais journalisée (la table de diagnostics 15 note le nombre d'octets et le résultat, jamais le texte ni la clé). Sans la table, le hub n'offre pas la transcription. **Garde-fous de la clé** : `url` doit être en `http://` ou `https://` avec un hôte explicite (nom ou IP) ; la clé n'est envoyée qu'à cet hôte exact, sans redirection, sans proxy d'environnement ; le fichier de clé est lu comme des lignes `NOM=valeur`, jamais exécuté ni « sourcé » ; la config est celle de la personne qui possède le hub, pas d'un membre, donc l'URL n'est jamais fournie par une page ou un document. Une table invalide arrête le démarrage avec l'erreur de config habituelle. Le fichier de clé doit être d'accès 0600, sinon le hub refuse de l'utiliser et le dit une fois (comme le fait le reste de la config de sécurité, 9.1 : [non vu] à aligner sur la règle exacte).

## Comment le hub sait si la transcription est disponible

Objectif : jamais de bouton mort. La disponibilité est **calculée par qui fait le service**, pas devinée par la page.

**Hub du laptop.**

- Le hub garde un état `transcribe: {available, checked_at}`, rafraîchi **à la demande** et gardé 30 s : pas de fil de fond, pas d'événement. La vérification fait deux appels, délai 3 s chacun : `GET {url}/status`, sans clé [vu : `whisper.ready: true` le 2026-11-12], puis `GET {url}/audio/gpu-status`, **avec** la clé, qui ne transcrit rien [vu : route de l'OpenAPI, `security: APIKeyHeader`; son contenu de réponse : **[non vu]**, à lire à l'implémentation]. Disponible = les deux répondent 200, `whisper.ready` vrai, clé lisible. Une clé révoquée ou fausse donne 401 au second appel : indisponible, donc pas de bouton.
- L'information arrive à la page par `GET /_/transcribe` (cookie ; réponse `{available: bool}`), demandé au chargement de la page et à chaque ouverture de la boîte (no meta field; availability comes only from GET /_/transcribe at load and at each box opening (decision Halima 2026-11-12: keeps t-compute out of page render)). Le meta de `_fresh_meta` ne change pas, et la réponse de montage non plus. Aucun nouvel événement du flux : le flux d'un membre n'admet que `proxy.DOCUMENT_EVENTS` [vu, handler.py:219] et ce relais n'existe que sur le port de bouclage (voir plus bas), donc rien à ajouter côté proxy. Une page déjà ouverte qui perd le service s'en aperçoit à la prochaine ouverture de la boîte, ou à l'échec d'un relais (le hub répond 503 `unavailable` et la page retire le bouton).
- Le seul cas de bouton qui échoue : le service tombe dans la fenêtre de 30 s entre deux vérifications, ou pendant que la boîte reste ouverte. L'appel échoue alors (503), la ligne d'erreur du point 6 s'affiche et le bouton disparaît. Il est dit à la personne, pas silencieux.
- **Le relais n'existe pas sur la socket proxy** : `/_/transcribe` répond 404 en mode proxy (la page montée parle à l'hôte), pour qu'un hub en mode proxy ne devienne pas un relais vers t-compute pour les membres d'Open WebUI sans décision de Thierry (décision A).

**Montée dans tiroir.**

- Le hub ne peut pas le savoir (il n'appelle pas l'hôte). La route existe sur Open WebUI 0.11.4 et utilise le moteur local `base` sans clé [vu, stt-read.md et stt-read-2.md], donc la seule absence connue est la permission `chat.stt` d'un compte. Le plan garde le repli : la page montée montre le bouton et le retire pour la session au premier échec, 403 compris, avec la ligne d'erreur. Aucune sonde par `GET` n'a été faite (Beatriz n'a appelé la route d'aucune façon) ; le plan **ne compte plus sur** une sonde 405. Ce repli laisse un cas de bouton qui échoue une fois (compte sans `chat.stt`, ou Open WebUI arrêté) ; il est écrit comme tel et non présenté comme « pas de bouton mort ».

## Politique de sécurité pour le micro (boîte 4)

**Étape 0 : lue le 2026-11-12, trois points restent non vus.** Lecture de Beatriz (2026-11-12, `stt-read-2.md`). Vu : aucune `Permissions-Policy` dans la chaîne (Caddy, Open WebUI, hub), donc rien ne bloque le micro ; la CSP d'Open WebUI (`object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'`, posée par Caddy) n'a ni `connect-src` ni `media-src`, donc le `fetch` de même origine n'est pas restreint. **Restent non vus, à lever avant le code de la page montée** : (1) si le volet monté par le chargeur est un iframe (alors `allow="microphone"` est nécessaire sur cet iframe) ; (2) les drapeaux du cookie `token` ; (3) les en-têtes de la page du hub une fois connecté (la page authentifiée n'a pas été récupérée). Le test d'en-tête du hub (point 7 ci-dessous) ne prouve rien pour la page montée.

Faits : la CSP actuelle est `default-src 'none'; script-src 'nonce-…'; style-src 'unsafe-inline'; img-src data:; font-src data:; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` (`'self'` sur la socket proxy) [vu, `auth.py:72`, SPEC 9.5]. Le hub n'envoie aucun en-tête `Permissions-Policy` [vu : recherche de « Permissions-Policy » et « microphone » dans `src/`, aucun résultat].

- **La CSP ne contrôle pas le micro.** `getUserMedia` n'est pas une directive CSP. Rien à ajouter à `script-src`, `media-src` ou `blob:` : le son part en `Blob` dans le corps d'un `fetch`, sans jamais passer par une URL `blob:`. `connect-src 'self'` suffit pour `/_/transcribe` sur le hub.
- **Politique de permissions.** Sans en-tête, le micro est permis pour la page de premier niveau et refusé aux iframes qui n'ont pas `allow="microphone"` [non vu ici ; règle standard des Permissions Policy, à vérifier à la main]. Plan : le hub envoie **explicitement** `Permissions-Policy: microphone=(self), camera=(), geolocation=()` sur chaque réponse HTML (une ligne dans `handler.py` à côté de la CSP, ligne 338 [vu]). Cela ferme caméra et géolocalisation que la page n'utilise pas, et nomme le micro. Dans la socket proxy, la page peut être encadrée par une page de l'hôte (`frame-ancestors 'self'`) : le micro y exigerait `allow="microphone"` sur l'iframe côté hôte. **Non vu** : aucun iframe n'a été observé dans la configuration actuelle de tiroir (la page est montée dans un shadow root, pas encadrée) ; le plan ne demande rien à l'hôte pour ce cas, et le test (plus bas) vérifie l'en-tête, pas le comportement d'un iframe.
- **Page montée.** Elle vit dans le document d'Open WebUI, en shadow root (pas d'iframe dans `mount.js`, mais le chargeur de l'hôte n'a pas été lu : voir étape 0). Politique d'Open WebUI [vu, `stt-read-2.md`] : CSP sans `connect-src` ni `media-src`, aucune `Permissions-Policy`, `frame-ancestors 'self'`. Le micro est donc permis au premier niveau et la requête vers `/api/v1/audio/transcriptions` est permise.
- **Demande de permission.** Le navigateur demande l'autorisation à la première utilisation, jamais au chargement de la page : `getUserMedia` n'est appelé qu'au clic.
- **Ce que le son devient.** Il ne touche pas le disque du hub (corps en mémoire, 2 Mio max), n'est pas journalisé et n'est pas gardé. Sur le laptop, il quitte la machine vers t-compute par Tailscale (le réseau privé de Thierry) ; l'info-bulle du bouton reste « Dictate ».
- **Risque accepté par le mode proxy** (SPEC 9.9) : un script de l'origine agit comme la personne ; le micro ne l'aggrave pas parce que la permission est donnée par site, mais un script de l'origine pourrait déjà enregistrer sur le micro d'Open WebUI. Rien à changer.

## Ce qui est testé, et comment (sans vrai son en CI)

Aucun test de CI n'utilise de microphone ni de fichier audio réel : ils vérifient le câblage de la page et du relais (octets, en-têtes, extensions, erreurs), **pas** le décodage. Un conteneur invalide, un écart codec/extension ou le comportement de Safari ne sont attrapés que par le point 8, fait par une personne. Un petit fichier audio réel dans le dépôt n'y changerait rien tant que le faux t-compute ne le décode pas ; le test de décodage réel est une commande à la main contre t-compute (point 8). Les tests de page tournent sous Playwright [vu : `tests/page/test_page_chat_box.py`, marqueur `page`].

1. **Fausse capture** : un script d'initialisation de page remplace `navigator.mediaDevices.getUserMedia` par une fonction qui rend un `MediaStream` factice, et `MediaRecorder` par une classe factice qui émet un `Blob` de quelques octets (`b"RIFF…"`) avec le type demandé. On vérifie le comportement de la page, pas le codec. (Chromium offre aussi `--use-fake-device-for-media-stream` ; on ne s'en sert pas, pour que le test marche sans lui.)
2. **Hub de test et faux t-compute** : un petit serveur HTTP de test, lancé dans le test, joue `/api/v1/status` (`whisper.ready` vrai/faux), `/api/v1/audio/gpu-status` (200, ou 401 si la clé reçue n'est pas celle du fichier temporaire) et `/api/v1/audio/transcribe` (rend `{"text": "hello there", …}`, ou un 200 avec `error`, ou un 503). Le hub de test lit `[transcribe]` pointé vers ce faux serveur, avec un fichier de clé temporaire. On vérifie que le faux serveur a reçu `X-API-Key` (valeur du fichier temporaire, jamais une vraie), `X-Priority: high`, un nom de fichier à la bonne extension, et un multipart.
3. **Hub, sans page** (pytest direct, rapide) : `/_/transcribe` répond 401 sans cookie, 403 avec mauvais Origin, 413 au-delà de 2 Mio, 415 pour une extension non permise, 429 si un relais est en cours ; la réponse d'erreur ne contient jamais le texte brut de l'erreur de t-compute ni la clé ; la clé n'apparaît ni dans les lignes de diagnostic ni dans le corps d'une réponse ; sans table `[transcribe]` ou avec un fichier de clé trop ouvert, `transcribe` est faux dans le meta.
