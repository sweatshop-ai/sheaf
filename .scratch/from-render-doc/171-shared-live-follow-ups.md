- [x] **Events that land during a leader hand-over are not replayed** (`live.js`, `Leader.stop` and the `who` rejoin; found in the review of #484). When the leader freezes, closes or crashes, its stream ends, and the next leader opens a new one and every tab joins it again. An event the hub emits between the old stream closing and the tab's new join reaches no tab, and the stream has no event id to resume from. Read from `page.js:4468`: every join is answered by a `hello`, and `meetHello` runs `checkText()`, so a change to the document text in the gap is caught. Nothing in `meetHello` refetches comments, replies, agent progress or the index list, so an event of those kinds in the gap is lost until the next one of its kind. **Reproduction:** three tabs of one browser, the leader frozen (`Page.setWebLifecycleState` `frozen`, as in `test_a_frozen_leader_hands_the_stream_over_and_takes_it_back_on_resume`); while it is frozen and before a follower joins the new leader, post a comment from the API; assert the visible tabs show it within a few seconds. Do the same for the index page's list. **Proposed fix:** the hub numbers the events of each document and puts the latest number in `hello`; a page keeps the last number it saw and, when a `hello` carries a higher one that is not simply the next, refetches comments and replies (and the index its list) as `checkText()` does for the text. Cheaper first step: run that refetch on every `hello` after the first one of the page, since a `hello` after the first means the stream was re-opened. Acceptance: the reproduction passes with the leader frozen at the moment of the event. **Earlier the same day, before ticket 176:** the frozen-leader reproduction could not be run in CI. In headless Chromium, CDP `Page.setWebLifecycleState` `frozen` fires no `freeze` event and the leader holds `sheaf-live` for 40 s and more (ticket 176). PR #542, merged as 01e6939e (head 280a4f61, CI green, review GO round 4), covers the same gap with the leader closed instead: the comment written while every join is held reaches the visible tabs through `checkText` on the new `hello`. The acceptance does not count that, so item 5 waits on ticket 176. **Done with a simulated freeze (2026-11-22, ticket 176):** `test_a_comment_written_while_the_leader_is_frozen_reaches_the_tabs` freezes the leader by dispatching `freeze` (the tab sends nothing on its channels and what it receives waits until `resume`; no real freeze is reachable in CI, ticket 176), holds every join, waits until the hub counts no tab, writes the comment and has the hub take it in, then releases the joins: both visible tabs show the comment. With `checkText()` removed from `meetHello` the test fails. The comment is written to the file and taken in by `catch_up`, which emits the same `comments` event into the gap; it does not go through `/_/comment`. The index page's list is covered by reasoning, not by a test: the index page reads its list again on every `hello` (`soon()` in `page/index.js`), and while no index stream of any browser is joined the hub tells the index nothing (`touch` and `tick` in `hub/index.py` return when `index_bus.count()` is 0). With an index open in another browser, events do flow in the gap and this browser misses them; the `hello` refetch is what makes up for that. The numbered-events fix proposed above was not needed for this acceptance.
